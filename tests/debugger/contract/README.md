# debugger.contract: the debugger's server against the contract of the devtools UI

The server of the emulator (`libswirl/debugger`: the transport, the core, the emulator side) speaks protocol v3
with the devtools UI. The UI repository has the contract runner that holds a server to that protocol
(`npm run contract`, `scripts/contract/`); the tests of this directory start the emulator and run it, and test
what belongs to the server and is no scenario of the runner.

    python3 tests/debugger/contract/contract.py --emulator <nulldc3> --work /tmp/w --guest <2ndmix.elf> \
            --mode m1 --devtools <dreamcast-devtools checkout> --keep

Every emulator is started as `tests/system` and the selftests start one: headless (`config:Headless=yes`), no
audio device, its files in a directory of its own under the work directory (`--portable <dir>`), an empty
environment (no display), the real-time clock pinned, a core size limit of 1 byte and a watchdog; a process is
ended by its pid. The tests run on the emulator that the system tests build (`<build dir>/system/emulator`, or
`-DNULLDC_EMULATOR=`), and are skipped where those are. No embedded UI bundle is needed. One test runs no emulator:
`debugger.contract.hash.listening.rule`, which is there wherever python3 is.

`contract.py` starts the emulator and the contract runner through `tests/common/emurun.py`, the run helper of the
harnesses, and reads their output through it (a `\r` in front of a `\n` is not part of a line). On Windows the
emulator's environment is `SystemRoot` (without it Winsock does not start: `WSAStartup` fails with 10106) and `TEMP`
and `TMP` in the run's directory, the runner is `npm.cmd` (`NULLDC_NPM`; the `npm` beside it is a shell script),
and both run inside `nulldc3-winrun` (`NULLDC_WINRUN`, which the tests project passes), whose job ends `npm.cmd`, the
`cmd.exe` it runs and every `node` behind it when the run is ended: Windows has no SIGTERM, and ending the process
by its pid is ending that job. `tests/system` builds no emulator there: `-DNULLDC_EMULATOR=` is `nulldc3.exe` of an
emulator build, and the tests are skipped without it. The runner runs on Windows, from a checkout of the UI with
`npm ci` made there, against `127.0.0.1`. On macOS the emulator's environment is `TMPDIR` in the run's directory, the
runner's the caller's with `TMPDIR` and npm's cache in the work directory, and both run through
`tests/macos/macrun.py` (the sandbox profile that denies the window server, the Dock and LaunchServices, or the one a
long step runs under; a session of its own, which `macrun.py` kills with everything below it when the run is ended).
`-DNULLDC_EMULATOR=` is the executable of an emulator build's bundle there,
`<build>/nulldc3.app/Contents/MacOS/nulldc3` (`tests/system` builds none); without it, or with one that names no
file, the tests are tests whose data is missing. The runner runs from a checkout of the UI on the Mac with `npm ci`
made there, against `127.0.0.1`.

All the others but twelve boot `2ndmix.elf` of `NULLDC_ELF_DIR` (the KallistiOS example: it runs under reios, starts the
ARM7, has a `.symtab`, entry `0x8C010000`); `debugger.contract.m2arm7.guest`, `.m2writes.guest`, `.m2.guest`,
`.m3dsp.guest`, `.m3dsp21.guest` and `.hash.listening.guest`, each with its `.interp`, boot the sounding guest of the tree,
`tests/debugger/guest/dsptest/dsptest.elf`. The tests that run the contract runner need the
dreamcast-devtools checkout with its `node_modules` (`-DNULLDC_DEVTOOLS_DIR=`) and `npm`; without them they are
tests whose data is missing.

`nulldc_debugger_contract` of `CMakeLists.txt` has the option `GUEST <program>` for a test on another program than
2ndmix (such a test does not ask for `NULLDC_ELF_DIR`), and `contract.py` the mode `parts`, for a package that
delivers a part of a scenario of the runner: `--parts <scenario>:<part>[+<part>...]` and every `--require-note
<text>` are handed on to the runner (as `--only S00,<scenario> --parts ...`), and its exit code and summary are
taken. `contract.py` reads no note itself. The mode `m2` is the gate of milestone M2, `--milestone M2`; with the
option `ONLY <scenarios>` of the function (`--only` of `contract.py`) it is the second run of that gate, and it hands
on every `--require-note` as the mode `parts` does. The mode `m3` is the gate of milestone M3, `--milestone M3`, and
the mode `m3dsp` its second run, `--milestone M3 --dsp-program` against the sounding guest, which hands on every
`--require-note`. The mode `dsp` is the run of the gate of milestone M3 that holds the run control of the DSP by
itself, `--milestone M3 --dsp-program --only S00,S21` against the sounding guest, and hands on every
`--require-note` too.

## The engine of a run

Every run is made on the engine its test asks for, or the test fails, and says the engine it found and the one it
asked for. A test whose run took another engine would pass for one of the engine it names: up to f640f21a an
emulator that ignored `Debugger:ForceFallback` passed every `.fallback` test, and one that ran the fallback for
every run passed `debugger.contract.m2` on the JIT (the mutants `nofallback` and `allfallback` of the M2 gate).

* **The SH4.** `--engine jit` is `config:Dynarec.Enabled=yes`, `--engine interp` is `=no`; the emulator takes the
  first for a wish (a build without a recompiler goes on with the interpreter) and says `Using MCPU Recompiler` or
  `Using MCPU Interpreter`. Every run that has a machine has to say the line of its engine and not the other: every
  test but `config`, whose runs end before a machine exists.
* **What executes the SH4's breakpoints and steps**, by the name `debugger.describe` gives it among its
  capabilities: `sh4-debug-fallback` with `--fallback` (`Debugger:ForceFallback=yes`, the `.fallback` tests);
  `sh4-debug-native` on the recompiler without it (the tests without a suffix: on an x86-64 host, whose recompiler
  executes them itself; the recompiler of another host has no native breakpoints and reports the fallback, which
  is what the test asks for there); and `sh4-debug-native` on the interpreter (the `.interp` tests), which
  executes its breakpoints and steps itself, with the key or without it. `--fallback` with `--engine interp` is
  refused. The tests that run the contract runner ask for `debugger.describe` on a connection of their own when
  the runner has ended (`m1`, `m2`, `m2arm7`, `m2writes`, each on the engines it has); `grace` and
  `hash.listening` take the describe of their own clients at the `StartPaused` stop, `slow`, which has no such
  stop, the describe its client makes once the machine runs (a describe that is answered before the machine has
  selected its engine names neither capability); `hash.idlebp`, whose emulator ends with its run, takes the
  capabilities from the last `server:` line that the runner prints (one for its first describe, and one more
  for the describe it makes at the `StartPaused` stop when it connected before it). `hash.off` and
  `hash.noclient` have no client, and check the SH4 alone. The engine is printed: `engine: the SH4 on the
  recompiler, its breakpoints and steps on sh4-debug-fallback, as asked`.

## The address of the idle breakpoint

`hash.idlebp` is about a breakpoint that is listed, armed and never stops (R5 and R13 of the design on a real
program): the blocks of its page are compiled with the check, the check answers "continue" at every arrival.
That says something only for an address the program arrives at; a muted breakpoint reports nothing, so an address
that is never executed would pass the test as well (the entry `0x8C010000` runs once, at the boot, and is such
an address).

The symbol the CMake line names is `stars_one_frame` (`_stars_one_frame`, `0x8C010748` in the 2ndmix.elf the
test was written with): the function of 2ndmix that moves and draws its star field, called from the main loop
once in every frame. That it is reached was shown with the server itself: the emulator at its `StartPaused`
stop, an enabled breakpoint on the symbol with nothing muted, and `control.runUntil` twelve times in a row. Every
resume was followed by the stop of that breakpoint (`reason: "breakpoint"`, PC `0x8C010748`): the first 262 ms
after the resume (the boot and the set-up of the program, 166 frames of emulated time), the second within the
same frame (the program calls the function twice before its first frame is over), and every one after that
1.6 to 3.5 ms after its resume and 3,335,817 to 3,337,097 SH4 cycles after the stop before it, which is one
frame of 59.94 Hz (3,336,670 cycles). The selftest `core.guest` stops on the same symbol.

`debugger.contract.grace` has its breakpoint on the same function, enabled, for the same reason: on an address
that is never reached again (the entry) a cleared active mask and breakpoints that are active again look alike.
The price is that the state at the moment a client connects cannot be asked for: the connect makes the breakpoint
active, the target reaches it 2 to 3 ms later, and a `debugger.describe` sent right behind the connect is
answered in front of that stop in most runs and behind it in the others. So the test asks nothing. It takes the
stop as it is sent, which says when it was made, and the SH4's time in the ticks of the two stops, which says how
far the target ran in between.

## Where the mock of the UI repository and this server differ

Both implement the protocol, and the runner passes on both. Where they differ the design decides; these are the
differences that a client could see (design section in brackets):

* `breakpoints.setCategoryStates`: the mock validates the value of every key of `categories`, also of keys that
  are no category, and answers `-32602` for a malformed one; this server does not look at keys that are no
  category at all (3.3: unknown keys ignored).
* The device tree: the paths, the parents and the two register panels of milestone M2 are the same; the register
  lists are each server's own (M2-ROUND 3.6.1). This server has 2949 registers on 92 of its 104 nodes, the fields
  of the 64 channels among them (38 each); the mock has a few on each node. `DMEA` of `dc.aica.common` is 23 bits
  in both; `L` and `M` are 8 bits here and 3 in the mock.
* Register writes: this server writes the registers of the two processors, `dc.sh4.cpu` and `dc.aica.arm7` but
  `ENABLED`, and answers `-32013` for every other register (milestone M2); the mock writes the registers of
  every node unless it is started as an M2 server (`MOCK_M2_SUPPORT`, `--mock-support m2` of the runner), which
  is this server's set. What a write does to the machine is the emulator's alone: a written PC of the SH4, or an
  FPSCR with another PR, SZ or rounding mode, empties the code cache of the SH4; a written SR that lets an
  interrupt in has it accepted when the stop is left.
* `symbol` of a callstack frame: `name` at the start of a symbol and `name+0x<offset>` inside it here (2.10);
  the mock writes `name+0x0` at the start. The hex digits of `symbol` and `location`: lower case here (2.10),
  upper case in the mock; a client accepts either.
* `sp` of a scanned callstack frame: the stack pointer of the processor here, the same in every frame (3.2); the
  mock gives the address the frame was found at.
* Memory: the mock's ARM7 has the RTC at `0x00810000`; here the ARM7 sees wave memory and the AICA register
  file only (2.7).
* The targets: both step the SH4, the ARM7 and the DSP (milestone M3: the DSP's 128 steps execute in every sample
  whatever the ARM7 does, in both); both have the SGC capture and the memory binary.
* The capture's response and its stop with reason `capture`: this server publishes the stop on the emulator thread
  and its core thread sends the response when it takes the capture's notice, so the two reach a client in either
  order (design 3.3); the mock sends the response first. A capture's frames and a memory read go in one binary
  frame behind their response; the transport counts binary messages apart from text (64 MiB and 16 MiB), so a frame
  of 32 MiB leaves room for every tick behind it.
* The tick that follows a request that changed the tables is sent from inside the call, on the emulator thread,
  and can reach the client in front of the response of that request; the mock sends the response first (2.9
  allows both).
* The grace period: when it expires the mock releases the stop without an entry in the event log; this server
  appends `dc.debugger.note` (2.6, 2.9).
* A describe of a client that names another protocol number is logged as `dc.debugger.note` here (2.6); the
  mock logs nothing.
